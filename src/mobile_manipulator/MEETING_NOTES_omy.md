# 주간 미팅 자료 — 최신 OpenMANIPULATOR-Y(OMY) URDF 직접 제작 + 뎁스 카메라 구동

> 슬라이드 7장, 발표 5분 기준. 각 장 = 제목 / 핵심 메시지 / 본문(표·불릿) / 발표 멘트.
> 모든 수치는 2026-10-05 실측 또는 URDF에서 계산한 값 (ROS 2 Humble, Gazebo Classic 11).
> 값 옆 표시 — **[Gazebo]** Gazebo 시뮬레이션 실측, **[RViz]** RViz 전용 mock 모드 실측, **[계산]** URDF/코드로 계산, **[사양]** ROBOTIS 공식 자료.
> 그림은 `docs/omy/` (부록 A). 코드는 `omy_description`, `omy_bringup`, `omy_gazebo_plugins` 패키지, 사용법은 `README_omy.md`.

## 1. 이번 주 목표와 진행 흐름

**핵심 메시지** — 지난주 OMX 분석, SCARA·UR식 6축 설계에 이어서, ROBOTIS의 최신 매니퓰레이터 OMY를 실제 제품 수준으로 직접 URDF로 만들었다. 뎁스 카메라로 물체를 찾아 집는 것까지 구동했다.

**교수님 지시 해석**
- "OMX 말고 최신 OpenManipulator를 직접 URDF로 작성해서 구동"
  - 최신 모델은 OpenMANIPULATOR-Y (OMY)
- "depth camera 달린 것"
  - D405 카메라와 그리퍼가 기본으로 달린 **OMY-F3M**
- 지난주 UR식 6축은 치수를 마음대로 정한 가상 로봇이었다. 이번에는 **실제 제품의 도면, 관성, 모터 사양을 그대로 맞추는 것**이 차이점이다.

**진행 흐름**
OMY 사양 조사 → URDF 작성 (팔, 그리퍼, D405) → 공식 모델과 수치 검증 → Gazebo 구동 → 집기 문제 해결 → 카메라로 인식해서 집기 → (Gazebo 접속 불가) RViz 전용 모드와 가짜 D405 → 영상 저장

**결과 요약**
- 직접 작성한 URDF를 ROBOTIS 공식 모델과 비교했다. 무작위 자세 1000개에서 손끝과 카메라 위치 오차가 **0 mm**였다 [계산].
- Gazebo에서 큐브를 **5회 연속 집어서 옮겼다** [Gazebo]. 이를 위해 문제 5가지를 풀었고, 그중 하나는 C++ 플러그인을 직접 만들어 해결했다.
- D405로 큐브 위치와 방향을 재서 집었다. 파란 큐브의 yaw는 29.0°로 쟀다 (실제 28.6°) [Gazebo, RViz].

**발표 멘트** — "이번 주에는 지난주에 연습한 방식으로 실제 최신 제품인 OMY를 만들었습니다. 이번에는 숫자를 제가 정하지 않고 실물과 맞추는 것이 목표였습니다."

## 2. OpenMANIPULATOR-Y (OMY) 소개

**핵심 메시지** — OMY는 산업용에 가까운 6축 팔이다 (가반하중 3 kg, 무게 13.5 kg). 종류가 4가지이고, 그중 그리퍼와 D405 카메라가 달린 F3M을 대상으로 했다.

**종류** [사양]

| 모델 | 구성 |
|---|---|
| OMY-L100 | 원격 조종용 리더 장치 |
| OMY-3M | 6축 팔만 (손끝 장치 없음) |
| **OMY-F3M** | **6축 팔 + 2지 그리퍼(RH-P12-RN-A) + Intel RealSense D405** ← 이번 대상 |
| OMY-AI3M | L100 + F3M 세트 (모방학습용) |

**OMY-F3M 사양** [사양]

| 항목 | 값 |
|---|---|
| 자유도 | 6 |
| 구동기 | joint1·2는 YM080-230-A099-RH (최대 61.4 Nm), joint3~6은 YM070-210-A099-RH (최대 31.7 Nm) |
| 가반하중 / 도달 거리 / 무게 | 3 kg / 580 mm / 13.5 kg |
| 관절 범위 | joint3 ±150°, 나머지 ±360° |
| 반복 정밀도 | ±0.05 mm |

**발표 멘트** — "OMX는 0.6 kg짜리 교육용 4축이었는데, OMY는 13.5 kg에 3 kg을 드는 6축이라 규모가 완전히 다릅니다. 이 중 카메라가 달린 F3M을 만들었습니다."

## 3. URDF 구조와 검증

**핵심 메시지** — xacro 6개 파일(600줄)을 직접 작성했다. 치수는 도면, 관성은 CAD 값, 모터 한계는 데이터시트에서 가져왔다. 공식 모델과 비교해서 오차가 없음을 확인했다.

**파일 구성** (`omy_description/urdf`, 6개 파일 600줄) [계산]

| 파일 | 줄 | 역할 |
|---|---|---|
| `omy.urdf.xacro` | 71 | 최상위. `variant:=f3m/3m`로 모델 선택, world에 고정, 그리퍼와 카메라 장착 위치 |
| `omy_arm.xacro` | 185 | 치수 property, link0~6, joint1~6, 플랜지 |
| `rh_p12_rn_a.xacro` | 89 | 그리퍼 (손가락 2개 × 마디 2개, 평행 링크) |
| `d405.xacro` | 118 | 카메라 본체, 광학 프레임, Gazebo 뎁스 센서 |
| `omy_ros2_control.xacro` | 79 | Gazebo는 팔 velocity / 그리퍼 effort, RViz mock은 둘 다 position |
| `omy_gazebo.xacro` | 58 | 마찰, 플러그인 |

**데이터 출처**

| 항목 | 출처 |
|---|---|
| 관절 위치, 관절 범위 | 사양서와 도면 |
| 형상 | ROBOTIS CAD STL 메시 (OMX와 같은 방식, `scale="0.001"`) |
| 질량, 무게중심, 관성 | ROBOTIS CAD 값 (팔). 그리퍼와 카메라는 바운딩 박스 기준 균일 밀도 공식 |
| 충돌 형상 | 각 STL의 바운딩 박스를 직접 계산 |
| 토크·속도 한계 | DYNAMIXEL-Y 데이터시트 |

**지난주 UR식 6축과 비교** — 축 순서 z-y-y-y-z-y가 **같다**. 직접 설계한 구조가 실제 제품과 같은 UR 타입이었다.

| 관절 | 축 | UR식 6축 (가상) 위치 (m) | OMY (실제) 위치 (m) |
|---|---|---|---|
| joint1 | z | (0, 0, 0.10) | (0, 0, 0.1715) |
| joint2 | y | (0, **+**0.07, 0) | (0, **−**0.1215, 0) |
| joint3 | y | (0, −0.06, 0.22) | (0, 0, 0.247) |
| joint4 | y | (0, 0, 0.20) | (0, +0.1215, 0.2195) |
| joint5 | z | (0, 0.05, 0) | (0, −0.113, 0) |
| joint6 | y | (0, 0, 0.05) | (0, 0, 0.1155) |

- 다른 점: 치수가 약 1.2배이고, 옆 방향 오프셋의 부호가 반대이며, 팔꿈치 오프셋이 joint3가 아니라 joint4에 있다.

**검증** [계산]

| 항목 | 결과 |
|---|---|
| ROBOTIS 공식 URDF와 순기구학 비교 (무작위 1000 자세) | 손끝, 카메라 위치 오차 **0 mm**. 그리퍼 손끝 0.09 mm (공식은 π/2 대신 1.57을 씀) |
| 전체 질량 | 13.37 kg (사양 13.5 kg) |
| 수평 도달 거리 (joint1 축 ~ 플랜지) | 0.582 m (사양 580 mm) |
| 생성 URDF (F3M) | 링크 19 / 관절 18 (움직이는 관절 10) |

**발표 멘트** — "구조는 지난주에 만든 UR식 6축과 같아서 그 경험을 그대로 쓸 수 있었습니다. 다른 점은 숫자를 전부 실물에서 가져왔다는 것이고, 공식 모델과 비교해서 위치 오차 0 mm를 확인했습니다."

## 4. D405 뎁스 카메라

**핵심 메시지** — 카메라를 URDF에 넣고 시뮬레이션에서 컬러, 깊이, 포인트클라우드를 받았다. 이 데이터로 큐브의 3D 위치와 방향을 쟀다.

**모델링**
- 본체 42×42×23 mm, 손목(link6) 위 브래킷에 장착하고 렌즈는 손끝 방향을 향한다.
- 프레임 구조 (REP-103): `camera_link` (x 앞) → `camera_depth_optical_frame` (z 앞, x 오른쪽, y 아래). 포인트클라우드는 optical 프레임 기준이다.
- 센서 설정 [사양]: 시야각 87°, 848×480, 측정 거리 0.07~0.5 m

**큐브 인식 방법** (`omy_pick_demo.py`)
1. 준비 자세에서 테이블을 내려다본다.
2. 컬러 영상에서 목표 색 픽셀을 찾는다.
3. 같은 픽셀의 포인트클라우드 좌표를 모은다 (D405는 컬러와 깊이가 같은 센서라 픽셀끼리 1:1 대응).
4. TF로 로봇 기준 좌표로 바꾼다. 가장 높은 면의 점 평균을 윗면 중심으로 쓴다.
5. yaw는 윗면 점들을 투영했을 때 폭이 가장 작은 각도로 정한다 (변 방향이면 0.04 m, 대각선이면 0.057 m).

**측정 결과**

| 큐브 | 측정 (x, y, z / yaw) | 실제 |
|---|---|---|
| 빨강 [Gazebo, RViz] | (0.450, 0.000, 0.140) / 0.0° | (0.45, 0, 0.14) / 0° |
| 파랑 [Gazebo, RViz] | (0.380, 0.180, 0.140) / 29.0° | (0.38, 0.18, 0.14) / 28.6° |

**겪은 문제** — Gazebo 포인트클라우드의 색이 빨강과 파랑이 뒤바뀌어 나왔다. 영상은 정상이라 플러그인 문제로 판단했다. 그래서 색은 영상에서 판단하고 좌표만 포인트클라우드에서 가져오게 했다.

**그림** — `docs/omy/d405_color.png`, `docs/omy/d405_depth.png`, `docs/omy/detection_red.png`, `docs/omy/detection_blue.png`

**발표 멘트** — "카메라가 본 영상에서 큐브를 찾고, 깊이 정보로 3D 위치와 회전을 쟀습니다. 돌아간 파란 큐브의 방향도 0.4° 차이로 맞췄습니다."

## 5. Gazebo에서 집기 성공까지

**핵심 메시지** — 처음에는 큐브를 밀기만 하고 들지 못했다. 원인 5가지를 하나씩 찾아서 해결했고, 결과는 5회 연속 성공이다.

| # | 문제 | 원인 | 해결 |
|---|---|---|---|
| 1 | 손가락이 큐브를 뚫고 들어가고 쥐는 힘이 없음 | position 명령이 매 스텝 관절 각도를 덮어씀 | 그리퍼를 **effort(힘) 제어**로 (오차 → PID → 토크, 최대 2 Nm) |
| 2 | effort로 바꾸자 손가락 속도가 NaN (발산) | 손가락 관성 1e-5 kg·m²에 감쇠 0.7을 explicit 방식으로 적용 → 1 ms 스텝에서 불안정 | 손가락 관절에 `implicitSpringDamper` |
| 3 | 손끝 마디가 꺾이고, 양쪽 손가락이 어긋나서 큐브를 한쪽으로 밀어냄 | ros2_control의 mimic은 같은 토크만 줄 뿐 각도를 맞추지 않음 | **C++ Gazebo 플러그인 직접 제작** (`parallel_finger`, 71줄). 매 스텝 나머지 3개 관절을 구동 관절의 실제 각도에 맞춤 = 실제 그리퍼의 링크 기구 |
| 4 | 쥐었는데 들어 올리면 미끄러져 떨어짐 | 팔도 position이라 순간이동 → 링크 속도 0 → 마찰이 큐브를 끌어올리지 못함 | 팔을 **velocity 명령 + PID**로 |
| 5 | 3회 중 2회 실패 | 큐브 윗부분 1.8 cm만 쥠 | 집는 높이를 1.5 cm 낮춰서 3 cm를 쥠 |

- 참고: 설치된 gazebo_ros2_control 0.4.10의 position PID 기능은 플러그인 전체에 한 번에 적용되고 mimic 관절에 명령이 전달되지 않는다. 소스 코드를 읽고 확인해서 쓰지 않았다.

**결과** [Gazebo]

| 항목 | 값 |
|---|---|
| 집어서 옮기기 | 5회 연속 성공, 놓은 위치 (0.359~0.362, −0.198) / 목표 (0.35, −0.20) |
| 팔 추종 오차 (velocity + PID, TF로 측정) | 0.6 mm 이하 |
| 놓은 위치 약 1 cm 오차 | 팔 오차가 아니라 쥐는 동안 큐브가 패드 폭 방향으로 밀린 만큼 |

**발표 멘트** — "시뮬레이션에서 물체를 집는 게 생각보다 어려웠습니다. 그리퍼가 실제로는 링크 기구로 움직이는데 시뮬레이터는 그걸 표현하지 못해서, 플러그인을 직접 만들어 재현했습니다."

## 6. RViz 전용 모드와 영상 저장

**핵심 메시지** — Gazebo가 접속되지 않는 상황이 생겼다. 그래서 RViz만으로 같은 데모가 돌도록 가짜 하드웨어와 가짜 D405를 만들었다. 카메라 영상 저장 기능도 추가했다.

**RViz 전용 모드** (`rviz_mock.launch.py`)
- ros2_control의 mock 하드웨어가 명령을 그대로 상태로 돌려준다. Gazebo와 같은 컨트롤러 이름을 써서 데모 코드는 수정하지 않았다.
- **가짜 D405** (`fake_d405_scene.py`)
  - 테이블과 큐브를 마커로 표시한다.
  - 카메라 위치에서 848×480 픽셀마다 광선을 쏴서(ray casting) 상자와 만나는 점을 계산한다.
  - Gazebo와 같은 토픽으로 내보낸다.
- 그리퍼가 닫히는 순간 손끝 3 cm 안의 큐브를 손에 붙이고, 열면 아래 테이블 위에 내려놓는다.

| 비교 (같은 자세) | Gazebo D405 | 가짜 D405 |
|---|---|---|
| 깊이 범위 | 0.319 ~ 0.459 m | 0.319 ~ 0.459 m |
| 빨간 큐브 픽셀 수 | 3136 | 3136 |
| 포인트클라우드 색 | R/B 뒤바뀜 | 정상 |

- 겪은 문제
  - 렌더링(약 0.2 s)이 단일 스레드에서 돌면서 그리퍼가 닫히는 순간을 놓쳤다.
  - 팔이 움직이는 중의 프레임으로 위치를 잘못 계산했다.
- 해결: 멀티스레드로 바꾸고, 포인트클라우드를 찍은 시각의 TF를 쓰게 했다.
- 결과 [RViz]: 팔을 똑바로 세운 자세에서 시작해도 빨강, 파랑 모두 인식해서 (0.350, −0.200)에 놓았다.

**영상 저장** (`save_d405.py`)

| 모드 | 저장 파일 |
|---|---|
| 사진 한 장 | `color.png`, `depth_mm.png` (16비트 mm), `depth_vis.png`, `points.ply` (40만 점), `camera_info.json` |
| 동영상 | `color.mp4`, `depth_vis.mp4` |
| 집기 데모 `save:=true` | 위 파일 + `detection.png` (인식 결과 표시) |

**그림** — `docs/omy/pick_sequence.png` (카메라 시점 4컷: 테이블 보기 → 접근 → 쥐고 이동 → 내려놓음)

**발표 멘트** — "시뮬레이터가 안 될 때도 작업을 이어갈 수 있도록 카메라를 직접 흉내 내는 노드를 만들었습니다. 같은 자세에서 Gazebo 카메라와 같은 값이 나오는 것을 확인했습니다."

**한계**
- **손끝 높이:** 그리퍼를 아래로 향하면 손끝을 약 0.39 m보다 높이 올릴 수 없다 (joint4 최대 높이 0.638 m − 손끝 길이 0.244 m). 팔 치수에서 나오는 구조적 한계다.
- **무작위 목표 IK:** 작업 공간 안 무작위 목표 200개 중 75%만 풀렸다. 실패한 목표에는 원래 도달할 수 없는 위치도 섞여 있다.
